## Third pass: the real cause of the hang, and how far Calculator gets now (2026-11-20, evening)
* **The hang was a kernel bug in darwinator, not LaunchServices.** With `kern.darwinator.debug=1` the kernel's own check printed `ulock ... changed without a wake: 0x1886902 -> 0 (lost wakeup)`: the lock word went back to 0 while a thread slept. Cause: `ulock_wait` returned 0 always. XNU returns the number of OTHER waiters of the address, and libplatform's `os_unfair_lock` uses it (a woken waiter that sees more waiters takes the lock without the "no waiters" bit, so its unlock wakes the next one). Without it the second waiter slept for ever. Fix in `darwinator/src/syscalls_posix.c` (waiter list under `ulock_sx`, result = waiters left), test in `tests/c/syscalls.c` (two waiters), commit pushed. This also explains the hangs of the real Dock and lsd in the bring-up log ("lost wake-up or owner problem in psynch/ulock").
* With the new module (built on the dev VM from `/tmp/isowork/src/usr/src/sys`, loaded with `kldunload darwinator; kldload /tmp/darwinator.ko`; run `sysctl kern.darwinator.dyld=1 two_volumes=2 fast_sleep_ms=5` again after) and the stack of d/darwin (+ `lsd-objc` with an empty store) Calculator went through these walls, each one found by reading darwinator's trace (`debug=2`) and symbolising frames with the cache (`ipsw dyld a2f`, slide 0x1940C000):
  1. `LanguageIdentifier.c: stat(path) == 0` assertion: `/usr/share/langid/langid.inv` missing (also `/usr/share/icu/icudt78l.dat`): copied from the Mac VM and mounted with nullfs over the empty `/usr/share/langid`, `/usr/share/icu` of the image.
  2. `libobjc-trampolines.dylib` not found: `/usr/lib/libobjc-trampolines.dylib` and `libffi-trampolines.dylib` from the Mac VM into the `/usr/lib` overlay.
  3. `SwiftUICore/NamedImage.swift` trap (`ud2` after `SFSCoreGlyphsBundle` returned nil): `SFSymbols.framework` must be laid out as on a Mac (`Resources -> Versions/Current/Resources`, `Versions/Current -> A`, `Versions/A/Resources/CoreGlyphs.bundle` with the 154 MB `Assets.car`).
  4. Real AppKit: `NSImage imageNamed:` -> `NSCoreUIImageRepGetSystemAppearanceRenderer` threw (`dictionaryWithObjects:forKeys:` with nil): AppKit's own `Resources` (2 MB `Assets.car`, nibs, loctables) were not on the disk: copied from the Mac VM.
* **Result:** the process stays alive (state `machmsg`, 5.9 s CPU) and reaches **Metal**: `-[MTLIOAccelServiceGlobalContext init]: IOServiceAddMatchingNotification failed e00002c7` (kIOReturnUnsupported), repeated by several threads: real Metal.framework asks IOKit for the accelerator service that does not exist, so no MTLDevice. No window yet. This is the Metal wall of the plan.
* **What the image/macdeps must carry (not in the dyld cache, from the user's Mac):** `/usr/share/langid`, `/usr/share/icu`, `/usr/lib/libobjc-trampolines.dylib`, `libffi-trampolines.dylib`, the Resources of the frameworks the stack uses (AppKit, SFSymbols' CoreGlyphs, ...), SystemVersion data (ours, see above). A real list should come from tracing opens that fail (darwinator `debug=2`) over all the Apple apps we target. Later these data are replaced by free ones (NO-MAC roadmap steps 4-5).
* `lsd-objc` still dies of SIGSEGV after a while (`0x7ff81be365c2`, fault address 0x20) and its store is empty: not needed for this progress, still to do.

## Tenth pass (2026-11-21): latency of the window server, resources, and the first AttributeGraph abort
* **The "hang" in `get_current_display_system_state` was latency, not a missing reply.** `SLSGetDisplayForUUID` fetches `GetDisplaySystemState` (34003) every time: the client caches the state only while `cached->seed == display_system_state_seed`, and the global seed is updated only when display notifications are enabled (`set_cached_display_system_state`). So SwiftUI's `safeAreaInsets` -> `notchFrame` -> `currentSpace` asked about 4 times a second, and each round trip cost 100-270 ms because the window server of the 2026-11-19 image composes with GL on llvmpipe (CPU: 128 ms a frame, requests are served between frames). The current `WindowServer` repo already uses its software compositor under llvmpipe (commit 40d38d9). Replacing the image's binary by a fresh build (`gmake kms gl` on the dev VM, copied over the overlay file and restarted) made the same request take under a millisecond. The image has to be rebuilt with the current WindowServer.
* **Resources the real frameworks read from disk** (not in the cache, copied from the Mac VM into the VM overlay; to be listed in macdeps): `SwiftUI.framework/Versions/A/Resources` (Assets.car, loctables), `SwiftUICore.framework/.../Resources`, `/System/Library/CoreServices/SystemAppearance.bundle/Contents/Resources` (25 MB of .car). Without the last, `SwiftUI.CatalogAppearance.init(named:bundle:)` traps (`missingCatalog`).
* **Now:** the first update of SwiftUI's view graph aborts: `AG::non_fatal_precondition_failure` -> `abort` inside AttributeGraph (`Graph::update_attribute` nested through `AGGraphGetValue` / `AGGraphGetWeakValue`). The message is not visible (stderr stays empty even with `OS_ACTIVITY_DT_MODE=YES`, `AG_PRINT_CYCLES=1`); AttributeGraph keeps it in `AG::error_log()`. Tried and failed: interposing `AG::non_fatal_precondition_failure` (dyld: `Symbol not found`, the function is not exported by AttributeGraph in the cache). The symbolised frames of the abort are also unreliable (the kernel's backtrace scans the stack: `UpdateStack::cancel` only marks frames and cannot abort). Next: interpose `abort` itself (exported) from a probe library and print the thread's real unwind with `backtrace()`, or read AttributeGraph's `error_log` buffer; or run the same graph update on the Mac VM with `AG_PRINT_CYCLES=1 AG_TRAP_CYCLES=1` to see whether a cycle is the cause.

## Eleventh pass (2026-11-21): the real cause of the AttributeGraph abort

## Fourteenth pass (2026-11-21): a SwiftUI app reaches its main event loop
* `NSApplication finishLaunching` waited in a synchronous XPC call to appleeventsd (`_AERegisterCurrentApplicationInfomationWithAppleEventsD`, found with `tools/pearos-where.sh`, which symbolises the main thread's stack): `com.apple.coreservices.appleevents` was not served (`NOT FOUND` in launchd's log, and libxpc waits). `lsd-stub com.apple.coreservices.appleevents` (the same stub, one more name on its command line) answers; `Hello` then passes `finishLaunching` and sits in `-[NSApplication run]` -> `nextEventMatchingMask:` -> `CFRunLoopRun`: **the app is fully launched and idle, as a real app waits for events.**

## Twenty-second pass (2026-11-21): the fence observer protocol (REA on QuartzCore 26.7.2)
`CA::Render::Fence::Transaction::Observer::activate` (block at 0x7ff80d3ce855) is a `dispatch_mach` handler on a port of the client; the real render server sends two kinds of message to it, parsed by `CA::Render::Fence::extract_msg`:

## Ninety-second pass (2026-11-23): why the Mac does not trap, and the tunables
* **`-[NSScrollView _updateTitlebarAdjacencyState]` decompiled** (REA on the extracted AppKit): it reads the window (`[self window]`), `_hasFullSizeContentView`, the scroll view's frame against the window's content layout rect (`convertRect:fromView:`), `NSSolariumEnabled()`, several private flags, and **registers the scroll view with the window section controller (`registerScrollViewSeparatorTrackingAdapter:`) only when the geometry test and the flags say the scroll view touches the titlebar area**; otherwise it creates an `NSScrollViewMirrorView` or nothing.
