## Third pass: the real cause of the hang, and how far Calculator gets now (2026-11-20, evening)
* **The hang was a kernel bug in darwinator, not LaunchServices.** With `kern.darwinator.debug=1` the kernel's own check printed `ulock ... changed without a wake: 0x1886902 -> 0 (lost wakeup)`: the lock word went back to 0 while a thread slept. Cause: `ulock_wait` returned 0 always. XNU returns the number of OTHER waiters of the address, and libplatform's `os_unfair_lock` uses it (a woken waiter that sees more waiters takes the lock without the "no waiters" bit, so its unlock wakes the next one). Without it the second waiter slept for ever. Fix in `darwinator/src/syscalls_posix.c` (waiter list under `ulock_sx`, result = waiters left), test in `tests/c/syscalls.c` (two waiters), commit pushed. This also explains the hangs of the real Dock and lsd in the bring-up log ("lost wake-up or owner problem in psynch/ulock").
* With the new module (built on the dev VM from `/tmp/isowork/src/usr/src/sys`, loaded with `kldunload darwinator; kldload /tmp/darwinator.ko`; run `sysctl kern.darwinator.dyld=1 two_volumes=2 fast_sleep_ms=5` again after) and the stack of d/darwin (+ `lsd-objc` with an empty store) Calculator went through these walls, each one found by reading darwinator's trace (`debug=2`) and symbolising frames with the cache (`ipsw dyld a2f`, slide 0x1940C000):
  1. `LanguageIdentifier.c: stat(path) == 0` assertion: `/usr/share/langid/langid.inv` missing (also `/usr/share/icu/icudt78l.dat`): copied from the Mac VM and mounted with nullfs over the empty `/usr/share/langid`, `/usr/share/icu` of the image.
  2. `libobjc-trampolines.dylib` not found: `/usr/lib/libobjc-trampolines.dylib` and `libffi-trampolines.dylib` from the Mac VM into the `/usr/lib` overlay.
  3. `SwiftUICore/NamedImage.swift` trap (`ud2` after `SFSCoreGlyphsBundle` returned nil): `SFSymbols.framework` must be laid out as on a Mac (`Resources -> Versions/Current/Resources`, `Versions/Current -> A`, `Versions/A/Resources/CoreGlyphs.bundle` with the 154 MB `Assets.car`).
  4. Real AppKit: `NSImage imageNamed:` -> `NSCoreUIImageRepGetSystemAppearanceRenderer` threw (`dictionaryWithObjects:forKeys:` with nil): AppKit's own `Resources` (2 MB `Assets.car`, nibs, loctables) were not on the disk: copied from the Mac VM.
* **Result:** the process stays alive (state `machmsg`, 5.9 s CPU) and reaches **Metal**: `-[MTLIOAccelServiceGlobalContext init]: IOServiceAddMatchingNotification failed e00002c7` (kIOReturnUnsupported), repeated by several threads: real Metal.framework asks IOKit for the accelerator service that does not exist, so no MTLDevice. No window yet. This is the Metal wall of the plan.
* **What the image/macdeps must carry (not in the dyld cache, from the user's Mac):** `/usr/share/langid`, `/usr/share/icu`, `/usr/lib/libobjc-trampolines.dylib`, `libffi-trampolines.dylib`, the Resources of the frameworks the stack uses (AppKit, SFSymbols' CoreGlyphs, ...), SystemVersion data (ours, see above). A real list should come from tracing opens that fail (darwinator `debug=2`) over all the Apple apps we target. Later these data are replaced by free ones (NO-MAC roadmap steps 4-5).
* `lsd-objc` still dies of SIGSEGV after a while (`0x7ff81be365c2`, fault address 0x20) and its store is empty: not needed for this progress, still to do.

## Tenth pass (2026-11-21): latency of the window server, resources, and the first AttributeGraph abort
* **The "hang" in `get_current_display_system_state` was latency, not a missing reply.** `SLSGetDisplayForUUID` fetches `GetDisplaySystemState` (34003) every time: the client caches the state only while `cached->seed == display_system_state_seed`, and the global seed is updated only when display notifications are enabled (`set_cached_display_system_state`). So SwiftUI's `safeAreaInsets` -> `notchFrame` -> `currentSpace` asked about 4 times a second, and each round trip cost 100-270 ms because the window server of the 2026-11-19 image composes with GL on llvmpipe (CPU: 128 ms a frame, requests are served between frames). The current `WindowServer` repo already uses its software compositor under llvmpipe (commit 40d38d9). Replacing the image's binary by a fresh build (`gmake kms gl` on the dev VM, copied over the overlay file and restarted) made the same request take under a millisecond. The image has to be rebuilt with the current WindowServer.
* **Resources the real frameworks read from disk** (not in the cache, copied from the Mac VM into the VM overlay; to be listed in macdeps): `SwiftUI.framework/Versions/A/Resources` (Assets.car, loctables), `SwiftUICore.framework/.../Resources`, `/System/Library/CoreServices/SystemAppearance.bundle/Contents/Resources` (25 MB of .car). Without the last, `SwiftUI.CatalogAppearance.init(named:bundle:)` traps (`missingCatalog`).
* **Now:** the first update of SwiftUI's view graph aborts: `AG::non_fatal_precondition_failure` -> `abort` inside AttributeGraph (`Graph::update_attribute` nested through `AGGraphGetValue` / `AGGraphGetWeakValue`). The message is not visible (stderr stays empty even with `OS_ACTIVITY_DT_MODE=YES`, `AG_PRINT_CYCLES=1`); AttributeGraph keeps it in `AG::error_log()`. Tried and failed: interposing `AG::non_fatal_precondition_failure` (dyld: `Symbol not found`, the function is not exported by AttributeGraph in the cache). The symbolised frames of the abort are also unreliable (the kernel's backtrace scans the stack: `UpdateStack::cancel` only marks frames and cannot abort). Next: interpose `abort` itself (exported) from a probe library and print the thread's real unwind with `backtrace()`, or read AttributeGraph's `error_log` buffer; or run the same graph update on the Mac VM with `AG_PRINT_CYCLES=1 AG_TRAP_CYCLES=1` to see whether a cycle is the cause.

## Eleventh pass (2026-11-21): the real cause of the AttributeGraph abort

## Fourteenth pass (2026-11-21): a SwiftUI app reaches its main event loop
* `NSApplication finishLaunching` waited in a synchronous XPC call to appleeventsd (`_AERegisterCurrentApplicationInfomationWithAppleEventsD`, found with `tools/pearos-where.sh`, which symbolises the main thread's stack): `com.apple.coreservices.appleevents` was not served (`NOT FOUND` in launchd's log, and libxpc waits). `lsd-stub com.apple.coreservices.appleevents` (the same stub, one more name on its command line) answers; `Hello` then passes `finishLaunching` and sits in `-[NSApplication run]` -> `nextEventMatchingMask:` -> `CFRunLoopRun`: **the app is fully launched and idle, as a real app waits for events.**

## Twenty-second pass (2026-11-21): the fence observer protocol (REA on QuartzCore 26.7.2)
`CA::Render::Fence::Transaction::Observer::activate` (block at 0x7ff80d3ce855) is a `dispatch_mach` handler on a port of the client; the real render server sends two kinds of message to it, parsed by `CA::Render::Fence::extract_msg`:

The window order-in animation (`_NSWindowTransformAnimation`, which stops "with display link") runs **32 steps on the Mac, 1 on pearOS**; SwiftUI renders from the same cycle.  `UpdateCycle` imports only Foundation / CoreFoundation: it is a CFRunLoop state machine (observer, timer, source), the tick comes from a timer; CVDisplayLink is not used (`tools/msgtrace.c` wraps `CVDisplayLinkStart`: never called).
* **Direct test** (`tests/appkit-hello`, `NSView displayLinkWithTarget:selector:` on the content view, added to the common run loop modes, counted for 3 s): **Mac 176 ticks (59 Hz), pearOS 0** (not paused).  `CA::Display::DisplayLink` (QuartzCore: `start_timer_locked`, `update_timer_locked`, `align_phase_locked`, `set_display_active`, `power_changed`, `display_power_changed`) is a timer driven link that depends on the *display being active*.  Equal on both sides (checked): `CGDisplayIsActive/Online/Main/Asleep`, `NSScreen.maximumFramesPerSecond` 60, refresh 60 Hz, 1920x1080.  The RealtimeDisplayInfo page is static on the Mac too (dumped three times during an animation), so it is not the source.
* Next: find what `CA::Display::DisplayLink` needs to start its timer on pearOS (`set_display_active`, the display power notification, a CADisplay object from QuartzCore that is filled from the render server's reply or from SkyLight), with `msgtrace` on the Mac (what is asked / delivered when the link starts) and by decompiling `CA::Display::DisplayLink::update_timer_locked` and `set_display_active`.
* **Decompiled (QuartzCore, REA):** `CA::Display::DisplayLink::update_timer_locked(bool)` reads the **refresh interval of the display** as a double at `display + 0x200` (or `+0x210`, chosen by bit 3 of the byte at `+0x261`); **if it is `<= 0` the timer is invalidated and the link never ticks**; otherwise it makes a `CADisplayTimer` (`CADisplayTimerCreate`, an `mk_timer` armed with `mk_timer_arm_leeway`) with that period and adds it to the run loops.  `CA::Display::Display::update` (the object that fills `+0x200`) starts from a default of 1/60 s and takes the real value from the display's mode data: either a MIG call to the render server (**id 0x9d28**, reply 0x9d8c, a mode list / refresh blob; not seen from the Mac's `akh`, nor by `carender-stub`) or from a local display object; `ModeSet::set_mig_representation` only builds the set of mode ids.
* So the question for the next pass is **who supplies the refresh interval on the Mac** (not the RealtimeDisplayInfo page, not 0x9d28 as far as the trace shows) and what our `CA::Display` object ends up with (`CADisplayLink` created by AppKit's `NSView displayLinkWithTarget:` gets 0 ticks).  Plan: interpose `CADisplayTimerCreate` (its period argument) in `msgtrace` on the Mac, and the same in a pearOS process through an extra dylib (`Metal/tools/trace-device/add-dylib.py`), to see the period each side passes (0 on pearOS would confirm), then find the field that feeds it.

## Forty-fifth pass (2026-11-22): the period of the display link on the Mac
* `lldb` (batch, `launchctl asuser 501`, `breakpoint set -a <cache address + slide>` of `CADisplayTimerCreate`, the slide of the Mac VM's cache is `0xeef9000`; `register read xmm0 xmm1`): the Mac creates the display link timer from `CA::Display::DisplayLink::update_timer_locked` ← `get_link` ← `DisplayLinkItem::update_link` with **period `0x3f9112cf90768542` = 0.0166733 s (59.99 Hz, a measured value, not 1/60)**; `CADisplayLink.maximumRefreshRate` (private, KVC) is `0.01667332` there.  Batch `lldb` prints the register dumps only for plain commands after `continue`, not from `breakpoint command add` blocks.
* On pearOS the values are **not stable between runs of the same program**: `NSScreen.maximumFramesPerSecond` was 60 / `minimumRefreshInterval` 0 in one run (like the Mac) and **2500 / 0.0004** in another, and the program stops after the "solarium" lines in that run (31 lines of output): the display object of CoreAnimation is filled by something asynchronous that the app does not wait for, or that fails on some runs.  Candidates: the 34003 `GetDisplaySystemState` blob and its decoding by QuartzCore (`CA::Display::Display::update` takes the mode data from SkyLight; the Mac's refresh is measured, ours is a constant 60.0 in the blob), the order of the replies, the `RealtimeDisplayInfo` page.

## Forty-sixth pass (2026-11-22): the mk_timer message
* **Cause of the dead display link found.** The expiry message of an `mk_timer` on the Mac is **48 bytes** (the header and three 64-bit words, all zero: `mk_timer_expire_msg_t`; `tools/msgtrace.c` saw `RCV id 0 size 48` with a zero payload); `darwinator` sent **40**.  `CA::Display::DisplayLink::callback(timer, u64, u64, u64, ctx)` takes its three arguments from those words, so with a short message it read bytes beyond the message and dropped the tick.  `mach_ipc.c` (`mk_timer_fire`) now sends 48 bytes.
* Result on the lab VM (`tests/appkit-hello`): the order-in animation advances (**50 `setCurrentProgress` calls, was 1**), the display link ticks (2 in 3 s in the run: the period it was given is **0.0004 s** because `CADisplay` still reports `maximumRefreshRate 0.0004` / `maximumFramesPerSecond 2500` in some runs; 60 Hz in others).
* **SwiftUI `Hello` is unchanged** (123 layers, 4 commits, white content): its update cycle still stops; also the refresh interval of the CoreAnimation display is not stable (60 Hz or 2500 Hz between runs).  Next: why the display interval varies (the order of the first replies of SkyLight / the render server) and what stops the SwiftUI cycle after its first commits.
* Test program note: `NSClassFromString(@"CADisplay")` blocks the program on pearOS (a class that does not exist; probably a slow path of the runtime): removed from `akh`.

## Forty-seventh pass (2026-11-22): the real GetDisplaySystemState blob
* `tools/msgtrace.c` dumps the reply of 34003 (`DSS:` lines).  On the Mac VM (26.7.2) it is **2484 bytes**: a header of 64 words (display id `0x31d491c0` at word 10, the display's sizes as doubles at 0x80 / 0xa0 / 0xc0, a MAC-address-like UUID at 0x60), **one current-mode record of 102 words at 0x100** (ids `4 0 1 0x2000007 0x2000007`, size 1280x800 twice, row bytes 5120, 110 dpi twice, scale 1.0, pixel-encoding strings, `0x3f003d`...) and **four 102-word and one 33-word records of 1x1 "virtual" modes** (flags `0x60000004`, `7`, the **60.0 float at word 5**: those are where 60.0 sits; the current mode has 0 there).  Our old template (`sls_display_tpl.c`: header 64 words, 33-word records, 16-word tail, from "a macOS runner") has another layout.
* `SkyLight/server/sls_display_mac.c` keeps the recorded blob; `WSD_DSS_26=1` serves it with our size patched in.  Effect on the lab VM: `CGMainDisplayID` becomes the blob's id (836014528: the client decodes the blob), `CGDisplayModeGetRefreshRate` 0.00 (on the Mac 60.00 comes from elsewhere), the order-in animation takes 136 steps (50 before) and the display link 1 tick.  Not the default: the refresh of the current mode is not yet understood (the Mac gets 60 Hz and a period of 0.0166733 s from IOKit / CoreDisplay timing, not from this blob).

## Forty-eighth pass (2026-11-22): the display timing is not in the blob, nor in the page we have
* The values are **not stable on the Mac either**: `akh2` prints `minimumRefreshInterval 0.000000` / `displayModeRefresh 60.00` in one run and `0.016673` / `0.00` in another (the one run under `msgtrace` and a re-signed binary).  The good Mac state has `NSScreen.minimumRefreshInterval` **= 0.016673 = the period the display link timer gets** (`CADisplayTimerCreate` 0.0166733); on pearOS the same field is 0 (the display link never starts: `update_timer_locked` returns when the interval is `<= 0`) or 0.0004 (2500 Hz).  So the period is **measured / delivered at run time**, not a constant of the mode record (the current mode of the 26.7.2 blob has no refresh value at all; 60.0 floats are only in the 1x1 virtual records).
* The Mac's first requests of an AppKit program in that phase: `34003` (display state) twice, then `30504` **GetRealtimeDisplayDataShmemPort** (ours answers it from the harvest: an error variant): a memory port to a 4 KB page (`WS::RealtimeDisplayDataMapping`), dumped by `msgtrace` (`RDD:` lines): not timing, a structure with pointers of the window server and a few floats (300.0, 753.98, 1.0); unchanged over 1.2 s.  The exported client names are not public (`_CGSGetRealtimeConsoleDisplayDataShmemPort`, `WSDisplayManagerGetRealtimeDisplayDataShmemPort`).
